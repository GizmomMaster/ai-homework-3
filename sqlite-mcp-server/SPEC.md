# sqlite-mcp-server — спецификация

## 1. Назначение

MCP-сервер, предоставляющий Claude доступ на чтение к локальной базе данных SQLite. Разработан как учебный проект (`ai-homework-3`), подключён к `sqlitedb/shop.db`.

**Ключевое требование:** сервер обязан быть **read-only**. Ни один инструмент не должен позволять изменять данные или схему базы, независимо от формулировки запроса пользователя/агента.

## 2. Архитектура и модель развёртывания

| Параметр | Значение |
|---|---|
| Транспорт | stdio (локальный процесс) |
| Язык / SDK | TypeScript, `@modelcontextprotocol/sdk` ^1.12.0 |
| Драйвер БД | `better-sqlite3` ^11.9.1 (синхронный, нативный биндинг к SQLite) |
| Аудитория | один пользователь / команда, локально — распространение не планируется |
| Апгрейд-путь | при необходимости раздавать сервер другим — упаковка в MCPB, чтобы не требовать установленный Node.js |

Сервер — обычный Node.js-процесс, запускаемый напрямую (`node dist/index.js`), без сети и без демонов.

### 2.1 Структура исходников

Код разбит по зонам ответственности; точка входа не содержит бизнес-логики.

| Модуль | Ответственность |
|---|---|
| `src/index.ts` | точка входа: конфиг → открытие БД → stdio-транспорт; перехват `ConfigError` → одна строка в stderr + exit 1 |
| `src/config.ts` | выбор пути к БД (`DB_PATH` / первый CLI-аргумент) и его резолв относительно корня проекта |
| `src/db.ts` | открытие соединения `readonly`, `quoteIdentifier()`, `tableExists()` |
| `src/errors.ts` | `ToolError` (отказ, показываемый вызывающему дословно) и `friendlySqlError()` (§6) |
| `src/sql-guard.ts` | слой 2 read-only-гарантии (§5): `assertReadOnlySelect()`, `assertNoOwnPagination()` |
| `src/server.ts` | сборка `McpServer` и регистрация наборов инструментов |
| `src/tools/register.ts` | общая обвязка регистрации: read-only-аннотации, `JSON.stringify` ответа, `try/catch` → `friendlySqlError` |
| `src/tools/schema.ts` | `list_tables`, `describe_table` (§4.1–4.2) |
| `src/tools/query.ts` | `run_query` (§4.3) |
| `src/tools/analytics.ts` | специализированные аналитические инструменты (§4.4–4.7) |

Хендлер инструмента возвращает обычные данные и не занимается сериализацией и
`try/catch` — это делает `registerReadOnlyTool()`. Отказ (например, несуществующая
таблица в `describe_table` или запрещённый SQL) выражается через `throw new ToolError(msg)`
и превращается в `isError: true` с текстом `msg`; любое другое исключение считается
ошибкой SQL и проходит через `friendlySqlError()`. Благодаря этому набор
read-only-аннотаций и формат ответа заданы в одном месте и не могут разъехаться между
инструментами.

**Экранирование идентификаторов.** Имя таблицы нельзя передать как параметр запроса, поэтому
в `PRAGMA table_info(...)` / `FROM ...` оно подставляется в текст SQL через
`quoteIdentifier()` — двойные кавычки с удвоением внутренних, по правилам SQLite. (Ранее
использовался `JSON.stringify`, который экранирует кавычку как `\"` — валидный JSON, но
невалидный SQL: имя вида `we"ird` приводило к `unrecognized token`. Закрыто тестом
`describe_table handles a table name that needs SQL quoting`.)

## 3. Конфигурация

| Переменная / аргумент | Обязательность | Описание |
|---|---|---|
| `DB_PATH` (env) | да, если не передан аргумент | Путь к файлу SQLite (абсолютный или относительный) |
| 1-й позиционный CLI-аргумент | альтернатива `DB_PATH` | Тот же путь |

Путь нигде не захардкожен в исходном коде. Если он не указан — процесс завершается с
понятным сообщением в stderr и кодом выхода 1, не запуская transport. Относительный
путь резолвится через `path.resolve` от корня проекта (`path.dirname(fileURLToPath(import.meta.url)) + "/.."`,
т.е. от директории, где лежит `package.json`), а не от `process.cwd()` — так путь работает
одинаково независимо от того, откуда MCP-хост запустил процесс.

БД открывается драйвером в режиме:

```ts
new Database(dbPath, { readonly: true, fileMustExist: true })
```

- `readonly: true` — файл открывается SQLite-движком с флагом `SQLITE_OPEN_READONLY`. Это защита на уровне БД/ОС, а не только на уровне логики приложения.
- `fileMustExist: true` — сервер не создаёт файл, если его нет (предотвращает случайное создание пустой БД по опечатке в пути).

## 4. Инструменты (tools)

Все инструменты помечены `readOnlyHint: true, idempotentHint: true, openWorldHint: false` и
имеют `title` + развёрнутый `description` (что делает, что возвращает, чего не делает, на
какой соседний tool переключиться — см. `references/tool-design.md` из скилла `build-mcp-server`).
Общего назначения — 3 tool'а, специализированных под частые аналитические вопросы — ещё 4.

### 4.1 `list_tables`

- **Параметры:** нет.
- **Возвращает:** JSON-массив таблиц БД (кроме служебных `sqlite_%`) с их колонками (`name`, `type`, `notNull`, `primaryKey`).
- **Назначение:** точка входа для агента — узнать, какие данные вообще есть.

### 4.2 `describe_table`

- **Параметры:** `table: string` — точное имя таблицы.
- **Возвращает:** схему колонок (`PRAGMA table_info`), количество строк (`COUNT(*)`) и до 3 примеров строк.
- **Валидация:** имя таблицы предварительно проверяется через `SELECT 1 FROM sqlite_master WHERE type='table' AND name = ?` (параметризованный запрос) — если таблицы нет, возвращается `isError: true` с подсказкой вызвать `list_tables`.

### 4.3 `run_query`

- **Параметры:** `sql: string` — один SQL-запрос без собственного `LIMIT`/`OFFSET`; `limit: number`
  (1–200, по умолчанию 100); `offset: number` (≥0, по умолчанию 0).
- **Возвращает:** `{ rows, returned, limit, offset, hasMore, nextOffset }` — страницу результата.
  `hasMore`/`nextOffset` позволяют агенту постранично пройти весь результат, не рискуя утонуть в
  тысячах строк за один вызов.
- **Пагинация — как это работает:** сервер выполняет `db.prepare(sql + " LIMIT ? OFFSET ?").all(limit + 1, offset)`
  — запрашивает на одну строку больше, чем нужно, чтобы понять, есть ли следующая страница, без
  отдельного `COUNT(*)`-запроса. `LIMIT`/`OFFSET` дописываются в конец исходной строки (а не
  оборачивают её в подзапрос), поэтому собственный `ORDER BY` пользовательского запроса
  сохраняется корректно между страницами — проверено тестом
  `run_query pages preserve the query's own ORDER BY`.
- **Ограничение количества строк:** `limit` валидируется схемой (`z.number().max(200)`) — запрос с
  `limit > 200` отклоняется ещё до вызова хендлера (`MCP error -32602`), а не тихо обрезается.
- **Назначение:** произвольные `SELECT`/`WITH ... SELECT`-запросы по базе. Description явно
  отправляет агента к специализированным tools (4.4–4.7) для типовых вопросов вида "топ N".

### 4.4–4.7 Специализированные tools

Введены, чтобы для частых аналитических вопросов агенту не приходилось каждый раз писать один и
тот же JOIN руками — меньше шансов на опечатку/неверный JOIN, и в описании сразу видно, что
именно tool делает.

| Tool | Параметры | Возвращает |
|---|---|---|
| `top_customers_by_spend` | `limit` (≤50, def. 10), `excludeCancelled` (def. `true`) | топ клиентов по `SUM(orders.total_amount)`: id, имя, email, `total_spent` |
| `top_selling_products` | `limit` (≤50, def. 10), `rankBy: "units_sold"\|"revenue"` (def. `units_sold`), `excludeCancelled` (def. `true`) | топ товаров: name, category, `units_sold`, `revenue` |
| `revenue_by_category` | `limit` (≤50, def. 10), `excludeCancelled` (def. `true`) | категории по выручке: category, `revenue`, `units_sold` |
| `customers_by_order_count` | `limit` (≤50, def. 10) | клиенты по числу заказов (все статусы): id, имя, email, `orders_count` |

Все четыре — `orders`/`order_items`/`products`-специфичны (жёстко заданы имена таблиц/колонок
магазина). Если этих таблиц в подключённой БД нет, SQL-ошибка `no such table` проходит через тот
же `friendlySqlError` (§6) и превращается в понятное сообщение, а не в падение — проверено тестом
`specialized tools report a friendly error ... against a database missing the expected tables`.

`top_selling_products` и `revenue_by_category` по умолчанию исключают позиции из `cancelled`-заказов
(join на `orders.status`), той же логикой, что и `top_customers_by_spend` — согласованность
проверена тестами (`excludeCancelled=false` возвращает те же числа, что были до введения фильтра).

## 5. Гарантии read-only-доступа

Требование: сервер должен **отказывать** в любых операциях изменения данных или схемы —
`INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE` и аналогичных, — и не должен позволять
агенту выполнить их даже при формулировках вида *"Delete all cancelled orders"*.

Защита реализована в три независимых слоя (defense in depth):

### Слой 1 — отсутствие write-инструментов

В сервере физически нет tool'ов `insert_row`, `update_row`, `delete_row` и т.п. Единственный способ
выполнить произвольный SQL — `run_query`, и он проходит через слои 2 и 3.

### Слой 2 — валидация текста запроса в `run_query` (`src/sql-guard.ts`, до вызова `db.prepare`)

Выполняется до передачи запроса в драйвер БД, в следующем порядке:

1. **Проверка префикса.** Regex `/^\s*(select|with)\b/i` — запрос обязан начинаться с `SELECT` или `WITH`. Любой другой statement (`DELETE ...`, `INSERT ...` и т.д.) отклоняется сразу.
2. **Запрет нескольких statement'ов.** Строка разбивается по `;`, непустые части считаются; если их больше одной — отказ (`"Only a single statement is allowed per call."`). Закрывает обход вида `SELECT 1; DELETE FROM orders;`.
3. **Блок-лист ключевых слов по всему тексту запроса**, а не только в начале:
   ```
   /\b(insert|update|delete|drop|alter|create|attach|detach|vacuum|pragma|reindex)\b|\breplace\s+into\b/i
   ```
   Это нужно, потому что SQLite поддерживает **data-modifying CTE** — синтаксически валидный запрос
   `WITH x AS (SELECT 1) DELETE FROM orders WHERE status='cancelled'` начинается с `WITH` и прошёл бы
   проверку №1. Блок-лист ловит `DELETE` (и остальные опасные ключевые слова) в любом месте строки.
   Также блокирует `PRAGMA` (может использоваться для трюков со схемой) и `ATTACH`/`VACUUM`.
4. **Запрет собственного `LIMIT`/`OFFSET`** (`/\b(limit|offset)\b/i`) — не про безопасность, а про
   корректность пагинации: сервер сам дописывает `LIMIT ? OFFSET ?` в конец запроса (§4.3), и если
   пользовательский SQL уже содержит `LIMIT`, получится синтаксическая ошибка вместо понятного
   ответа. Отклоняется заранее с явной подсказкой использовать параметры `limit`/`offset` инструмента.

Любое отклонение на этом слое возвращает `isError: true` с понятным текстом, объясняющим, что сервер read-only.

### Слой 3 — read-only соединение с БД (движок SQLite)

Даже если гипотетически слой 2 будет обойдён (например, новой SQL-конструкцией, которую не покрывает
блок-лист), соединение открыто с `readonly: true` → SQLite физически не даёт записать на диск и вернёт
ошибку `attempt to write a readonly database`, которая перехватывается в `try/catch` и возвращается
как `isError: true`. Этот слой не зависит от качества regex-фильтра и является окончательной гарантией.

### Проверено вручную (боевая проверка на `shop.db`, таблица `orders`, 102 записи `status='cancelled'`)

| Запрос | Результат |
|---|---|
| `DELETE FROM orders WHERE status='cancelled'` | отклонено на слое 2 (шаг 1) |
| `WITH x AS (SELECT 1) DELETE FROM orders WHERE status='cancelled'` | отклонено на слое 2 (шаг 3, обход префикс-проверки) |
| `SELECT 1; DELETE FROM orders WHERE status='cancelled';` | отклонено на слое 2 (шаг 2, stacked query) |
| `INSERT ...` / `UPDATE ...` / `DROP TABLE orders` / `ALTER TABLE ...` / `CREATE TABLE ...` | отклонены на слое 2 (шаг 1) |
| `PRAGMA writable_schema=1` | отклонено на слое 2 (шаг 1) |
| `SELECT id, status FROM orders WHERE status='cancelled' LIMIT 2` | выполнен, вернул строки |

Количество `cancelled`-заказов до и после прогона — без изменений (102/102).

Та же матрица (плюс обход через CTE и `;`-склейку) теперь закреплена автотестами в
`tests/read-only.test.ts` (§7) на детерминированной фикстур-базе, а не только разовой ручной проверкой.

## 6. Обработка ошибок

- **Старт процесса.** Открытие БД (`new Database(...)`) обёрнуто в `try/catch`: если файл не
  найден/недоступен, в stderr печатается одна строка `Could not open database at "<path>": <причина>`
  без Node.js stack trace, и процесс завершается с кодом 1 — до открытия stdio-транспорта.
- Несуществующая таблица в `describe_table` → `isError: true` + подсказка вызвать `list_tables`.
- Некорректный/запрещённый SQL в `run_query` → `isError: true` + объяснение причины отказа.
- **Понятные SQL-ошибки.** Любая ошибка выполнения запроса (во всех tools, не только `run_query`)
  перехватывается `try/catch` и прогоняется через `friendlySqlError()` — он распознаёт частые
  паттерны сообщений SQLite и переводит их в подсказку, что делать дальше, вместо сырого текста
  драйвера:
  - `no such table: X` → `Table "X" does not exist. Call list_tables to see the tables available...`
  - `no such column: X` → `Column "X" does not exist. Call describe_table on the relevant table...`
  - `syntax error` → `SQL syntax error: <msg>. Check for typos, missing commas, or unbalanced...`
  - всё остальное → `Query failed: <исходное сообщение SQLite>` (fallback, а не полный stack trace).
- Невалидные типы аргументов инструмента (например, число вместо строки) отклоняются SDK на этапе
  валидации схемы (`MCP error -32602: Input validation error: ...`) — до вызова хендлера.
- Ни одна ошибка внутри уже запущенного tool-вызова не приводит к падению процесса — транспорт stdio
  остаётся живым для следующих вызовов. Проверено вручную: невалидный тип аргумента, вызов
  несуществующего tool'а, запрос к несуществующей таблице, синтаксически некорректный SQL — во всех
  случаях в stderr пусто, в ответе только `isError: true` + текстовое сообщение.

## 7. Сборка, запуск, тесты

```bash
npm install       # установка зависимостей (better-sqlite3 собирается из исходников)
npm run build      # tsc: src/ -> dist/
npm run dev        # запуск через tsx без сборки (для разработки)
DB_PATH=/path/to.db npm start   # прод-запуск скомпилированной версии
npm test           # 53 автотеста (node:test); pretest сам вызывает npm run build
```

Тесты (`tests/*.test.ts`) не трогают `sqlitedb/shop.db` — каждый файл поднимает собранный сервер
как настоящий MCP stdio-процесс через `@modelcontextprotocol/sdk`-клиент
(`tests/client.ts`) и гоняет его против детерминированной фикстур-базы
(`tests/fixture.ts`, с заранее просчитанными ожидаемыми агрегатами в `EXPECTED`). Так тесты не
зависят от содержимого демо-БД, которое может быть пересоздано/изменено. Покрытие: read-only
гарантии (включая обходы), пагинация и сохранение порядка между страницами, понятные ошибки,
отсутствие stack trace (в ответах tools и при невалидном `DB_PATH` на старте), корректность всех
специализированных tools и их деградация на «чужой» схеме БД, наличие/длина `description` и
`readOnlyHint` у каждого tool'а, корректное экранирование «неудобных» имён таблиц.

Отдельно `tests/sql-guard.test.ts` проверяет чистые функции `src/sql-guard.ts` и
`quoteIdentifier()` напрямую, без запуска процесса: те же правила, что и в
`read-only.test.ts`, но провал такого теста сразу указывает на конкретную функцию, а не на
поведение сервера в целом.

## 8. Регистрация в Claude Code

Сервер зарегистрирован в **local**-scope (виден только текущему пользователю в этом проекте, не коммитится в git):

```bash
claude mcp add sqlite-shop -s local \
  -e DB_PATH=/home/gizmocoder/ai-homeworks/ai-homework-3/sqlitedb/shop.db \
  -- node /home/gizmocoder/ai-homeworks/ai-homework-3/sqlite-mcp-server/dist/index.js
```

Для командного использования через `.mcp.json` (`-s project`) потребуется заменить абсолютный путь к
БД на значение, которое каждый разработчик задаёт сам через переменную окружения — иначе конфиг не
будет переносимым между машинами.

## 9. Docker

`Dockerfile` — multi-stage: сборка (с `python3/make/g++` для нативного аддона `better-sqlite3`) →
рантайм-стадия без компилятора. Сервер общается по stdio, а не по сети, поэтому контейнер
запускается интерактивно (`docker run -i`, без `-t`), а файл БД пробрасывается как volume, а не
копируется в образ. Подробная команда — в [README.md → Docker](./README.md#docker).

**Проверено вживую** (`docker.io` 29.1.3 на Ubuntu 24.04, демон установлен и включён через
`systemctl enable --now docker`):

```bash
docker build -t sqlite-mcp-server .
```

Собрался без ошибок, итоговый образ — **338MB**. Дальше — полноценный MCP JSON-RPC round-trip
через `docker run -i` с `shop.db`, примонтированной как `:ro`-volume:

| Проверка | Результат |
|---|---|
| `initialize` | отвечает корректно |
| `tools/list` | все 7 инструментов на месте |
| `run_query "SELECT COUNT(*) FROM orders"` | `750` — совпадает с БД на хосте |
| `top_customers_by_spend` | те же данные, что и вне контейнера |
| `DELETE FROM orders` | отклонено, `isError: true` |
| `PRAGMA journal_mode` | отклонено, `isError: true` |

Read-only-гарантии и вся бизнес-логика работают в контейнере идентично прямому запуску на хосте;
нативный аддон `better-sqlite3`, собранный на стадии `build`/`prod-deps`, корректно линкуется в
финальной `node:20-bookworm-slim`-стадии (единый базовый образ между стадиями — это и было
условием ABI-совместимости).

## 10. Известные ограничения / что не входит в scope

- Запись (`INSERT`/`UPDATE`/`DELETE`) — намеренно не реализована; при необходимости потребуется
  отдельный набор write-инструментов с `destructiveHint: true` и явным подтверждением.
- Специализированные tools (§4.4–4.7) жёстко завязаны на схему `customers`/`orders`/`order_items`/
  `products` — на другой БД они вернут понятную ошибку через `friendlySqlError`, но не будут
  работать по смыслу; `run_query`/`list_tables`/`describe_table` остаются полностью общими.
- Нет поддержки нескольких одновременных подключений к разным БД — один процесс = один файл БД,
  заданный при старте.
- Не проверялось на других СУБД (MySQL/Postgres/MongoDB) — сервер специфичен для SQLite
  (`better-sqlite3`).
